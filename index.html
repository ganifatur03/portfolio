ingestion Python · market research client

Three days of clicking, replaced by one script

the problem

The client tracked Google Trends across a long list of markets. Collecting it meant opening the site, setting the filters, downloading one CSV, and repeating that for every country, every month. It took about three days of someone’s week, and a mistyped filter produced a file that looked perfectly normal.

what i built

I replaced the clicking with a Python job that calls the Trends API directly. The markets and search terms live in one configuration file, so adding a country is a line of text rather than another afternoon. The script pulls, normalises and writes every market in the same shape, ready to use, and runs on AWS Lambda so there is no machine to keep switched on.

what changed

The collection step stopped being a job anyone had to schedule time for. It can be re-run the moment someone asks for fresher numbers, and the output is identical every time.

orchestration AWS · client marketing team

One dashboard, ten sources that never agreed on a format

the problem

A marketing team wanted a single dashboard. Their inputs were a mix of vendor APIs and CSV files that arrived on their own schedules, in their own shapes, with their own ideas about what a date looks like. Before every refresh, someone had to stitch it all together by hand — which meant the dashboard was only as current as that person’s week.

what i built

An event-driven pipeline on AWS. Files and API pulls land in S3. A new object raises an EventBridge event, which starts a Step Functions workflow, and each step in that workflow is a Lambda doing one job: ingest, clean, validate, conform. Records that fail validation are held back and reported instead of quietly reaching the dashboard. The curated output goes to S3 and a Microsoft Fabric Lakehouse, which is what Power BI reads.

what changed

The refresh now starts when the data arrives, not when someone has an afternoon free. Splitting the work into separate steps also means a failure points at one stage rather than at the whole process.

ingestion Google Apps Script · no cloud platform

No cloud platform, no database? A pipeline inside a spreadsheet still works

the problem

This client’s data came from two places: an API, and a spreadsheet their team was still editing every day. There was no database and no cloud platform to put one on, and taking the spreadsheet away was not an option — people were working in it. Every time their side updated the sheet, the downstream data had to be corrected by hand.

what i built

A pipeline that lives where the data already lives. Google Apps Script pulls from the API and reads the working sheet, then writes both the current state and a dated snapshot into a separate spreadsheet. The working sheet stays theirs to edit; the snapshot keeps a history it never had before.

Because Power BI and Looker Studio both connect to Sheets directly, that is enough to feed a dashboard — no warehouse in between.

what changed

Edits on their side no longer mean rework on ours. For a dashboard that does not need a whole database behind it, this is the honest answer: match the architecture to the size of the problem rather than to the size of the tooling.

analysis Local LLMs · four datasets, twelve markets

AI-assisted insight: what stood out this month, read across every dataset at once

the problem

Every month the client’s data refreshed across four fronts at once — sales, advertising, market research and traffic to their own site — for twelve markets. Their analysts had to read all of it and work out how the month had performed. The hard part was never one dataset on its own; it was noticing that a dip in one of them lined up with a spend change in another. With that much to cover, those connections were found by chance or not at all.

what i built

An AI-assisted insight layer that reads the datasets together rather than one at a time. Each month it runs a cross-dataset pass over the curated data and writes up what actually stands out: the figures that moved unusually, where two sources tell different stories, and the questions an analyst should probably ask before going further.

The models are self-hosted with Ollama on a secure machine we control, not called out to a third-party API. Client data stays inside infrastructure we are accountable for, which is what made this acceptable to run on real figures.

what changed

Analysts now open the month with a list of leads instead of a blank dashboard, and several of those leads are connections they would not have gone looking for. It is explicitly a starting point, not a conclusion: every observation points back at the figures behind it, and the deeper analysis is still theirs to do.

Other things I do

side project

A personal assistant that remembers my own projects

I keep private notes on everything I work on, and after two years that is more than I can hold in my head. So I run a lightweight model locally with Ollama and put those notes behind a RAG setup, which lets me ask plain questions about my own history.

It answers the things I used to go digging for: how a particular metric was defined, which tools a project used, or what a piece of work was actually about. Everything stays on my own machine, which is the point.

how i work

Turning a business model into metrics, then into a dashboard

Building the pipeline is only half of it. Before any of it exists, I sit with clients, other teams and stakeholders to understand how their business actually makes money, what data they already hold, and what they are trying to decide.

That conversation becomes a set of metrics, and the metrics become a dashboard shaped around its purpose — monitoring and analysis are not the same screen. It is the part of the work that decides whether the rest of it gets used.
